## 1. Executive Summary

Task 6 of Phase 191 mandates a thorough forensic investigation of the market-data latency computations reported in Phase 190 (specifically the reported averages of ~205 ms for BTCUSD and ~3.94 seconds for ETHUSD).

Our forensic audit discovered a major clock-domain measurement flaw in the historical pipeline:
1. **Clock Skew Conflation**: The metric labeled "receive latency" was calculated as `receipt_utc - venue_timestamp_us`. However, the local host machine's system clock was ~326 ms to ~345 ms behind the Delta Exchange matching engine clock.
2. **Negative Delta Filter Artifact**: The pipeline discarded all negative deltas with the filter `0.0 <= latency_ms <= 60000.0`. Because the client clock was behind the exchange clock, **208 out of 209 BTCUSD frames** and **36 out of 37 ETHUSD frames** yielded negative deltas and were silently dropped!
3. **Sample Size N = 1**: The reported "average latency" of 204.96 ms for BTCUSD and 3,941.59 ms for ETHUSD was calculated from exactly **one frame each** ($N = 1$), which corresponded to the initial book snapshot generated by the venue server prior to client subscription!
4. **Resolution**: `core/research/l2_book_tracker.py` was hardened to separate clock domains: tracking unfiltered clock offset, local monotonic inter-arrival times, and exchange event intervals.

## 2. Clock Domain Separation & Formulation

To eliminate clock conflation, three distinct time domains are now explicitly distinguished:

```
[Matching Engine]                              [Client Host Interface]
Venue Event Time (t_venue) ------------------> Local Monotonic Receive Time (t_mono)
                                       ------> Local Wall-Clock UTC (t_utc)
```

1. **Exchange Event Time ($t_{\text{venue}}$)**: Timestamp generated by the Delta Exchange matching engine in microseconds (`ts`).
2. **Local Monotonic Time ($t_{\text{mono}}$)**: Nanosecond monotonic clock (`time.monotonic_ns()`). Strictly invariant to NTP jumps, system sleep, or wall-clock adjustments. Used to measure true local packet arrival dynamics and inter-frame intervals.
3. **Local Wall-Clock UTC ($t_{\text{utc}}$)**: Nanosecond UTC timestamp (`time.time_ns()`). Subject to local clock drift, NTP synchronization offsets, and leap seconds.
4. **Clock Difference ($\Delta_{\text{clock}}$)**:
   $$\Delta_{\text{clock}} = t_{\text{utc}} - t_{\text{venue}}$$
   This quantity represents the algebraic sum of one-way network transit latency ($t_{\text{transit}} > 0$) and the clock skew between host and venue ($\delta = t_{\text{host}} - t_{\text{venue}}$):
   $$\Delta_{\text{clock}} = t_{\text{transit}} + \delta$$
   If $\delta < 0$ and $|\delta| > t_{\text{transit}}$, $\Delta_{\text{clock}}$ is negative. A negative value is not "negative latency"; it is proof of host clock skew.

## 4. True Arrival Dynamics: Monotonic Inter-Arrival Time

Because one-way network latency cannot be accurately measured without sub-millisecond hardware PTP/NTP synchronization, true packet arrival dynamics must be evaluated using **monotonic inter-arrival intervals** ($\Delta t_{\text{mono}}$):

$$\Delta t_{\text{mono}}[i] = t_{\text{mono}}[i] - t_{\text{mono}}[i-1]$$

## 6. Audit Verdict & Guidance

**Latency Audit Classification**: **FLAW IDENTIFIED & REMEDIATED**

1. **Labeling Requirement**: Differences between incomparable clock domains must NEVER be reported as "network latency".
2. **Measurement Requirement**: Without synchronized PTP/NTP hardware clocks, orderbook arrival dynamics must be reported via monotonic inter-arrival distributions.
3. **Snapshot Handling**: Snapshot timestamps reflect venue state generation time and must not be blended into live incremental update stream latency statistics.
